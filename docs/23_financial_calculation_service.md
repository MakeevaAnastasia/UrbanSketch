# Серверный сервис финансовых расчётов

Дата: 24 ноября 2026 года, Europe/Moscow. Ветка: `feature/sprint-3-financial-calculations`.

## Назначение и архитектура

Реализован отдельный stateless-сервис `FinancialCalculationService` в каталоге `backend/UrbanSketch.Financial.Api/Calculations/`, предусмотренном планом docs/19. Он считает затраты, выручку, прибыль, ROI и рентабельность продаж по оригинальному ТЗ §5.1–5.4, §5.6 и §9 и границам третьего спринта. Правила строительных площадей продолжают docs/20–22.

Интерфейс:

```csharp
CalculationResult Calculate(FinancialModel model, ConceptVariant concept)
```

Сервис принимает явно переданные параметры модели и ТЭП концепции. Он не использует DbContext, HTTP, React, lazy loading, изменяемые поля экземпляра или глобальный кэш. Входные сущности и их сохранённые результаты не изменяются. Каждый вызов создаёт новый immutable record результата; списки возвращены как read-only коллекции. Один экземпляр пригоден для независимых параллельных вызовов.

В отличие от будущего orchestration-сервиса в широком плане docs/19, этот этап синхронный и не выполняет загрузку/сохранение. Регистрация DI, endpoint, fingerprint и работа с транзакциями отложены. Использование существующих типов сущностей не требует подключения к PostgreSQL.

## Состав файлов

- `Calculations/FinancialCalculationService.cs`: выбор и проверка используемых входов, вычисления, статусы и проверки возможности сохранения результатов.
- `Calculations/CalculationResult.cs`: типизированные результаты/категории и ошибки.
- `Calculations/ExactDecimal.cs`: внутренние точные операции над decimal без незаметного уменьшения дробной точности.
- `tests/UrbanSketch.Financial.CalculationTests/UrbanSketch.Financial.CalculationTests.csproj`, `Program.cs`: автономный console-runner по существующему стилю тестовых проектов, без БД.
- Этот документ.

Существующие незакоммиченные изменения предыдущих этапов сохранены. React, Program.cs, endpoints, EF-сущности, DbContext, обе миграции, snapshot и исходный JSON этим этапом не изменены.

## Входы и resolver

Из FinancialModel берутся восемь денежных параметров: ResidentialConstructionCost, CommercialConstructionCost, ParkingCost, ResidentialSalePrice, CommercialSalePrice, ParkingSalePrice, LandCost, AdditionalCosts. Два пользовательских overrides используются через существующий `ConstructionAreaResolver.Resolve(model, concept)`.

Из ConceptVariant берутся реализуемые ResidentialArea/CommercialArea, ParkingSpaces и исходные строительные ConstructionResidentialArea/ConstructionCommercialArea. Единый resolver выбирает отдельно для жилья и коммерции:

1. Override финансовой модели, включая явный 0.
2. Исходную строительную площадь концепции.
3. Null при отсутствии обоих источников.

Копии resolver нет. Реализуемые площади не подставляются в строительные. Пустые информационные ТЭП (жители, школы и т. п.) не влияют на расчёт. ProjectDuration не участвует в формулах текущего этапа; его положительность остаётся обязанностью действующего CRUD-контракта.

Сервис повторно проверяет именно используемые математические входы: площади — numeric(18,2), деньги — numeric(20,2), парковки — неотрицательный int. Недопустимы отрицательные входы, значения вне диапазона или с ненулевыми разрядами после сотых. Ноль допустим. Незадействованная исходная строительная площадь при наличии валидного override на результат не влияет.

Сущности используют non-nullable decimal для обязательных цен и реализуемых площадей: их нулевое значение нельзя отличить от неприсвоенного CLR default. Наличие обязательных полей при JSON-вводе обеспечивает существующая серверная валидация. Null вместо самой сущности — ошибка вызова (`ArgumentNullException`), не состояние пользовательского расчёта. Передающий код должен выбирать нужную концепцию по связи модели; сервис не загружает и не проверяет принадлежность сущностей через БД.

## Формулы

Обозначения: Bж/Bк — эффективные строительные площади; Sж/Sк — реализуемые площади; N — количество машино-мест; Cж/Cк/Cп — ставки строительства; Pж/Pк/Pп — цены продажи; L — земля; D — дополнительные расходы.

```text
Costs.Residential = Bж × Cж
Costs.Commercial  = Bк × Cк
Costs.Parking     = N × Cп
Costs.Land        = L
Costs.Additional  = D
TotalCosts = сумма пяти категорий затрат

Revenue.Residential = Sж × Pж
Revenue.Commercial  = Sк × Pк
Revenue.Parking     = N × Pп
TotalRevenue = сумма трёх категорий выручки

Profit = TotalRevenue − TotalCosts
Roi = Profit / TotalCosts × 100
SalesProfitability = Profit / TotalRevenue × 100
```

Предполагается продажа 100% реализуемых площадей и парковок. Строительные площади не используются для выручки. Земля и прочие расходы учитываются по одному разу. Налоги, индексация, кредитование и дисконтирование не добавлялись. Убыток и отрицательные проценты — допустимые результаты.

## Результат и неполные данные

`CalculationResult` содержит CostBreakdown с пятью категориями, RevenueBreakdown с тремя категориями, TotalCosts, TotalRevenue, Profit, Roi, SalesProfitability, а также Status, MissingInputs, Errors, PersistenceIssues и CanPersistToCurrentSchema. Числовые показатели nullable там, где расчёт может быть недоступен.

| Состояние | Семантика |
|---|---|
| Complete | Все необходимые входы известны и математические операции выполнимы точно. Нулевой знаменатель не мешает этому статусу |
| Incomplete | Отсутствует хотя бы одна эффективная строительная площадь; недостающие поля перечислены в MissingInputs |
| Failed | Есть недопустимый используемый вход или точный результат операции не представим в decimal; причина указана в Errors |

Если неизвестна строительная площадь жилья, Costs.Residential=null. Остальные достоверные категории сохраняются, но TotalCosts, Profit и оба коэффициента становятся null: сумма известных частей не выдаётся за полную стоимость. Выручка остаётся доступной, когда её собственные входы корректны. Аналогичный принцип применяется к ошибкам других категорий: зависимые агрегаты null, независимые показатели сохраняются.

MissingInputs содержит `constructionResidentialArea` и/или `constructionCommercialArea` — имена недостающих **эффективных входов**, а не обвинение конкретного источника. Даже неизвестная площадь при цене строительства 0 остаётся неизвестной. Условия статуса и списки позволяют будущему интерфейсу отличить неизвестность, ошибку и математически неопределённый коэффициент.

При TotalCosts=0 ROI=null. При TotalRevenue=0 SalesProfitability=null. Деление не выполняется; Infinity/NaN не возникают. При нулевых затратах и выручке Profit=0 и оба коэффициента null, статус Complete.

## Decimal, точность и переполнения

Входы и возвращаемые числа — decimal. Денежные операции не используют double/float. Простого `checked(decimal multiplication)` недостаточно: decimal иногда уменьшает scale, чтобы вместить большой результат, не выбрасывая исключение.

`ExactDecimal` раскладывает decimal на его точный знаковый 96-битный коэффициент и scale. Умножение и сложение коэффициентов выполняются BigInteger без ограничения разрядности, затем результат преобразуется обратно в decimal **только если представим точно**. Удаляются лишь незначащие конечные нули. Если коэффициент не помещается в 96 бит или необходимая шкала превышает 28, операция возвращает контролируемую ошибку `decimalOverflow` через сервис. Это защита десятичного результата, а не переход на приближённый числовой тип.

Переполнения произведения, суммы, разности и процента перехватываются на уровне отдельного показателя. Необработанные OverflowException наружу не выходят. Сервис не выдаёт зависимый aggregate после ошибки компонента. Слишком большие валидные входы не приводят к незаметному округлению или обнулению.

Суммы и произведения **не округляются**, включая промежуточные значения. Сотые входов могут дать четыре дробных разряда произведения. Например, 0.01 × 0.01 = **0.0001**, а не 0.00. Копейки сохраняются точно; при появлении долей копейки они не уничтожаются автоматически.

Проценты имеют явную политику: **4 дробных знака, MidpointRounding.AwayFromZero**. Используется точное рациональное деление коэффициентов с однократным округлением результата — без промежуточного округления отношения и без переполнения от предварительного умножения Profit × 100. Проверены положительная/отрицательная середины: +0.00005 → +0.0001, −0.00005 → −0.0001. Будущее отображение с двумя знаками тем же правилом превращает ROI 66.6667 в 66,67%.

## Возможность будущего сохранения

Текущие столбцы денежных итогов: numeric(20,2), диапазон ±999999999999999999.99. Roi и SalesProfitability: numeric(12,4), диапазон ±99999999.9999.

Сервис отдельно проверяет три денежных aggregate и два коэффициента:

- `storageRange`: значение вне диапазона существующего столбца.
- `storageScale`: значение нельзя записать с существующим scale без округления.

`CanPersistToCurrentSchema` истинен только при Complete и отсутствии PersistenceIssues. Математически точный результат может иметь статус Complete, но запрещать сохранение. Ошибка ёмкости decimal относится к Errors/Failed; несовместимость с более узкой PostgreSQL-схемой относится к PersistenceIssues. Эти состояния нельзя смешивать.

Например, расходы 50000000.0001 — точная сумма, но несовместима с numeric(20,2). Она возвращается для анализа с явным storageScale, не округляется скрыто до копеек. Диапазон допускаемых входов не гарантирует диапазон итогов, поэтому нельзя передавать результат напрямую в SaveChanges.

В следующем этапе можно отдельно рассмотреть миграцию трёх итоговых сумм в numeric(22,4), сохраняя 18 целых разрядов и точные доли копеек, как предложено в docs/19. Эта миграция всё равно не вместит все возможные произведения максимальных входов; явные ограничения диапазона останутся необходимыми. Альтернативная политика округления денежных итогов потребует отдельного явного решения и тестов. Сейчас схема PostgreSQL не менялась.

## Контрольный пример §9 ТЗ

Fixture явно задаёт Bж=Sж=1000, Bк=Sк=200, N=20, Cж=100000, Cк=80000, Cп=500000, Pж=200000, Pк=150000, Pп=1000000, L=14000000, D=10000000. Равенство строительных и реализуемых площадей — только данные этого примера.

| Показатель | Проверенное точное значение |
|---|---:|
| Затраты: жильё | 100000000 |
| Затраты: коммерция | 16000000 |
| Затраты: парковки | 10000000 |
| Земля / дополнительные расходы | 14000000 / 10000000 |
| Общие затраты | 150000000 |
| Выручка: жильё / коммерция / парковки | 200000000 / 30000000 / 20000000 |
| Общая выручка | 250000000 |

| Рентабельность продаж | 40% |

Проверяются все категории, а не только aggregate. Результат Complete и совместим с текущими типами хранения.

## Тестирование

Тестовый проект использует существующий формат автономного console-runner .NET 10. Первоначальный запуск до реализации подтвердил отсутствие Calculations; после реализации тесты прошли. Зависимости NuGet восстановлены без изменения пакетов приложения.

Команды из корня:

```powershell
dotnet build backend/UrbanSketch.Financial.Api --no-restore
dotnet run --project tests/UrbanSketch.Financial.CalculationTests --no-restore
dotnet run --project tests/UrbanSketch.Financial.ApiTests --no-restore
dotnet run --project tests/UrbanSketch.Financial.SeedTests --no-restore
dotnet ef migrations has-pending-model-changes --project backend/UrbanSketch.Financial.Api --no-build
```

CalculationTests покрывает:

- Контрольный пример; убыток; нулевую прибыль; нулевые затраты/выручку/все суммы.
- Неизвестную одну/обе строительные площади; доступную выручку и запрет неполных затрат/прибыли; неизвестную площадь при ставке 0.
- Override, исходную площадь, приоритет нуля; неизменность входов, независимость моделей и повторный расчёт после изменения цены/стоимости строительства/земли/дополнительных расходов.
- Невалидные отрицательные входы всех восьми денежных полей, отрицательные площади/парковки, точность и диапазон входов.
- Переполнение произведения, суммы и процента; случай скрытого уменьшения scale, который нельзя обнаружить одним checked.
- numeric(20,2) на точной границе и за ней; numeric(12,4) на границе и за ней; точное субкопеечное произведение; суммирование дробных компонентов без предварительного округления.
- Округление процентов на положительной и отрицательной середине; параллельные независимые расчёты одного экземпляра.

Итог: **44 теста расчётов, 104 существующих API-теста, 30 автономных тестов импортёра — 178 успешных проверок, 0 ошибок**. API runner использует изолированную SQLite; импортёр запущен без PostgreSQL-аргументов. Никаких запросов к основной базе для этих проверок не требуется.

Сборка backend успешна: **0 ошибок, 0 предупреждений**. EF подтверждает отсутствие изменения модели после последней миграции. Новые классы результата не зарегистрированы в EF и не становятся сущностями. Миграции не создавались, не изменялись и не применялись; пользовательские модели не читались/не изменялись через PostgreSQL.

## Подготовка следующего этапа

Математический сервис готов для отдельной интеграционной задачи. Потребуется загрузить связанную концепцию и модель, вызвать Calculate и обработать статус/ошибки, определить контракт частичного расчёта и проверку CanPersistToCurrentSchema, политику хранения дробных денег и актуальность сохранённых результатов. Одного `Roi == null` недостаточно для определения, выполнялся ли расчёт: null также обозначает нулевой знаменатель.

Текущий сервис не выполняет запись, не инвалидирует прежние результаты и не добавляет endpoint. Подключение к API/PostgreSQL, миграция точности при её выборе и интерфейс результатов требуют следующей отдельной задачи. Commit, push и переключение ветки не выполнялись.
