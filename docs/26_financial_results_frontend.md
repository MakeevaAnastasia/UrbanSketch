# React-экран результатов финансового расчёта

Дата: 25 ноября 2026 года, Europe/Moscow. Ветка: `feature/sprint-3-financial-calculations`.

## Цель и сценарий

Статический макет результатов заменён рабочим экраном «Результаты расчёта», подключённым к API из docs/24 и актуальной схеме PostgreSQL из docs/25. Все показатели приходят с сервера; финансовые формулы на клиенте не реализуются.

Пользователь выбирает концепцию, создаёт/открывает модель в финансовых параметрах, сохраняет входы, открывает результаты и нажимает «Рассчитать». Затем может вернуться к редактированию, сохранить новый параметр и пересчитать stale-результат. После перезагрузки модель выбирается по её серверному id, сохранённый расчёт читается через GET. Автоматическое восстановление выбранного id между перезагрузками не добавлялось.

## Экран и показатели

В заголовке показаны проект, концепция, реальный id финансовой модели и переход к параметрам. Без сохранённой выбранной модели показано понятное сообщение вместо вымышленных сумм. Кнопки «Рассчитать»/«Пересчитать» и «Обновить результат» имеют явные loading/disabled-состояния.

Карточки:

1. Общие затраты.
2. Потенциальная выручка.
3. Прибыль проекта, включая отрицательную.
4. ROI.
5. Рентабельность продаж.

Детализация затрат содержит жильё, коммерцию, парковки, землю, дополнительные расходы и итог; детализация выручки — продажи жилья, коммерции, машино-мест и итог. Использованы семантические dl/dt/dd, адаптивные карточки и существующие Tailwind-стили. Статические эталонные суммы и годовой график убраны с рабочего экрана. Существующий отдельный макет сравнения не расширялся; новые графики/потоки/сравнение/CSV не добавлены.

## REST API и DTO

- При каждом открытии экрана: `GET /api/financial-models/{id}/calculation`.
- Только по кнопке: `POST /api/financial-models/{id}/calculate`, без тела и клиентских сумм.

Расчёт не создаёт FinancialModel. Возвращается фактический backend-контракт: `state`, `isCurrent`, `result`; внутри result — status, costs, revenue, totalCosts/totalRevenue/profit/roi/salesProfitability, missingInputs, errors, persistenceIssues, canPersistToCurrentSchema.

Используется общий `requestJson`/ApiError, второй параллельный fetch-клиент не создавался. HTTP-модуль поддерживает opt-in acceptedStatuses; только calculate разрешает структурированный HTTP 422 как декодируемый ответ. Остальные вызовы сохраняют прежнее поведение обработки HTTP-ошибок. Серверные numeric-токены разбираются через существующие parseExactJson/JsonNumber/exactDecimal без потери знаков.

Decoder проверяет форму объектов, типы/статусы/списки ошибок, согласованность state и isCurrent, отсутствие чисел в not_calculated/stale. Current требует complete, пригодность сохранения, отсутствие ошибок/недостающих данных и известные денежные aggregate/категории. Неизвестные/сломанные ответы дают безопасную ошибку загрузки.

## Состояния и ошибки

| Состояние | Интерфейс |
|---|---|
| not_calculated | «Расчёт ещё не выполнен», кнопка запуска, без нулей и искусственных карточек |
| current | «Расчёт актуален», пять показателей и обе детализации |
| stale | Сообщение о необходимости повторить расчёт и «Пересчитать»; старые суммы скрыты |
| incomplete | Сообщение о нехватке данных, русские названия missingInputs, доступные частичные показатели; явная пометка «Частичный результат не сохранён» |
| error | Понятные сообщения о диапазоне/точности/входах, без отображения ошибочных числовых компонентов |

Для отсутствующего денежного показателя выводится «Нет данных». Null-коэффициент при известной прибыли отображается как «Не рассчитывается», в том числе при нулевом знаменателе. Если прибыль сама неизвестна из-за неполноты, коэффициенты отмечены «Нет данных», чтобы не смешивать причины отсутствия.

HTTP 400 использует безопасную действующую ошибку ввода; 404 сообщает, что модель не найдена; 409 предлагает обновить данные и повторить расчёт. Структурированный 422 показывает только безопасные сообщения по известным кодам ошибок и скрывает все числовые результаты. 500/сетевая недоступность дают понятную ошибку без stack trace и raw detail. Есть повторное чтение и повторный явный запуск. Произвольные технические сообщения из result.errors не вставляются в UI.

Новый сетевой тайм-аут не добавлялся: действующий общий клиент его не предусматривает. AbortController используется для отмены запросов при смене контекста/закрытии экрана. Неуспешный POST может завершиться на сервере при потере ответа; безопасное действие — «Обновить результат», которое читает сохранённый результат, а не создаёт новую модель.

## Актуальность, выбор модели и черновики

Актуальность определяет backend по fingerprint, клиент её самостоятельно не вычисляет. После возврата с параметров экран монтируется заново и читает состояние через GET; сохранение новых входов даёт stale, прежняя прибыль не остаётся текущей. GET не вызывает POST автоматически.

Выбранная модель сохраняется при переходах между вкладками через существующий useFinancialModels. Передаваемый modelId допустим только для загруженной сохранённой модели. При новой/невыбранной модели результат не запрашивается.

Прежний canDiscard/beforeunload-механизм сохранён: изменение параметров требует сохранить их либо явно подтвердить выход без сохранения. Без явного подтверждения переход блокируется. Сервер не получает несохранённый draft. Экран дополнительно блокирует расчёт при переданном dirty и предлагает сначала сохранить параметры. Обычный рабочий сценарий — сохранить входы, затем рассчитать. Подтверждённый отказ от черновика означает расчёт по прежним сохранённым входам.

Hook привязывает состояние к id, использует AbortController, возрастающий номер операции и проверку владельца текущего запроса. Ответ старой модели/концепции не может обновить новую; даже если mock transport игнорирует AbortSignal, номер/владелец защищают отображение. При новом запросе прежние данные очищаются, включая переход loading → error. Ref блокирует два синхронных POST ещё до следующего React-render. Изменения модели/закрытие экрана сбрасывают видимый контекст; отмена клиентского ожидания не гарантирует остановку уже начатого серверного POST.

## Форматирование decimal

Числовые результаты хранятся в клиентских DTO строками с точностью исходного токена. Decoder допускает полный диапазон decimal для частичных/ошибочных результатов, а не только numeric(20,2): сервер может вернуть точное число, которое невозможно сохранить. Такие error-компоненты не выводятся как результаты.

Форматтер использует строковое представление и BigInt только для **округления отображения**. Денежные суммы группируются пробелами, имеют максимум два дробных знака; проценты всегда два знака. Правило визуального округления — AwayFromZero, включая отрицательную середину. Не вычисляются итоговые суммы, прибыль или коэффициенты; данные для сохранения форматтер не изменяет.

Примеры: `150000000` → `150 000 000 ₽`, `999999999999999999.99` → `999 999 999 999 999 999,99 ₽`, `-100000000` → `-100 000 000 ₽`, `66.6667` → `66,67%`, `40` → `40,00%`. Точные большие decimal не преобразуются в JavaScript Number. Частичная достоверная денежная компонента с долями копейки показывается согласно требованию максимум двух знаков; исходная точная строка DTO не изменяется.

## Реальная проверка PostgreSQL

Использованы собственные проверочные backend **127.0.0.1:5196** и Vite **127.0.0.1:5176**, чтобы не завершать пользовательские процессы на 5079/5173. Backend запускается из актуальной сборки с реальными Development User Secrets; proxy направлен на этот экземпляр. Основная БД — прежняя локальная urbansketch_financial с тремя применёнными миграциями по docs/25. Схема не менялась.

Контрольный реальный цикл в Концепции А:

1. Создана собственная временная модель, её id подтверждён Location собственного POST.
2. Сохранены площади 1000/200, девять контрольных параметров ТЗ, земля 14 млн и дополнительные расходы 10 млн.
3. На results GET дал not_calculated; по кнопке POST вернул current с затратами **150 млн**, выручкой **250 млн**, прибылью **100 млн**, ROI **66,67%**, рентабельностью **40,00%**.
4. После перезагрузки выбран тот же серверный id, GET открыл сохранённый current.
5. Цена продажи жилья изменена на 210000, модель сохранена; GET дал stale, старые карточки скрыты.
6. Повторный расчёт вернул выручку **260 млн** и прибыль **110 млн**.
7. Через форму удалена только эта временная модель; последующий GET вернул 404.

До/после цикла raw-ответы GET списков финансовых моделей и GET ТЭП обеих концепций **полностью совпали**. Это подтверждает сохранность двух существующих моделей (параметров, overrides, итогов) и исходных ТЭП. Пользовательские проекты/концепции не удалялись, существующие модели не использовались для редактирования/расчёта. Harness в finally очищает только id из Location своих POST. Прежний полный браузерный CRUD площадей также сохранён и прошёл.

Дополнительная завершающая прямая SQL-сверка после браузерных тестов **не выполнена**: автоматическая проверка разрешений дважды истекла по тайм-ауту. Это не отменяет выполненного браузером сравнения до/после, но не выдаётся за отдельную SQL-проверку.

## Ограничения и готовность

Тестовые процессы backend **PID 1944** и Vite **PID 17256** на портах 5196/5176 на момент отчёта остались работать. Запрос на их остановку не прошёл автоматическое согласование по тайм-ауту; обычный Stop-Process для собственного backend получил Access denied, до остановки Vite цикл не дошёл. Пользовательские процессы не завершались. При необходимости завершить эти собственные тестовые экземпляры нужно повторно подтвердить их актуальные PID/командные строки; без проверки не использовать сохранённые PID, поскольку Windows может их переиспользовать.

Экран не опрашивает сервер непрерывно: внешние изменения обнаруживаются при открытии/кнопке обновления и очередном расчёте. Полноценная авторизация/ETag, тайм-ауты и непрерывные подписки не добавлялись. Неполный результат POST после перезагрузки не восстанавливается как сохранённый — это действующий backend-контракт. Финансовые формулы, схема и миграции не менялись. Денежные потоки, графики, сравнение, CSV, NPV/IRR не реализовывались; прежний отдельный макет сравнения остаётся макетом.

Функциональность готова к отдельной финальной приёмке спринта 3. Следующий этап, commit/push и переключение ветки не выполнялись.
