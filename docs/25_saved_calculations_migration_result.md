## Аудит Up и Down

Миграция добавляет:

| Поле FinancialModel | PostgreSQL | Nullable | Default |
|---|---|---|---|
| CalculationInputHash | calculation_input_hash character varying(64) | YES | нет |
| CalculationSnapshot | calculation_snapshot text | YES | нет |

Типы соответствуют FinancialDbContext и EF snapshot. Существующие денежные numeric(20,2), коэффициенты numeric(12,4), площади numeric(18,2), идентификаторы, связи, проекты и концепции не меняются. Старые модели совместимы: новые поля первоначально NULL, расчёт отсутствует.

Проверенный [Up-SQL](sql/add_saved_financial_calculations.sql) содержит транзакцию, два ALTER TABLE ADD и INSERT служебной записи в __EFMigrationsHistory. Нет DROP TABLE/COLUMN, DELETE, TRUNCATE, пересоздания таблиц, UPDATE прежних параметров или изменения numeric-точности.

Штатный Down удаляет только эти два новых столбца и теряет снимки расчётов. Он изучен отдельно и **не выполнялся**. Наличие стандартного Down не является дефектом Up.

## HTTP-проверки в тестовой копии

На восстановленной и мигрированной PostgreSQL выполнен существующий специальный runner:

```powershell
# Явное подключение к изолированной базе задавалось в окружении, без публикации credentials.
dotnet run --project tests/UrbanSketch.Financial.ApiTests --no-restore -- --calculation-postgres
```

Guard runner запрещает host, отличный от 127.0.0.1, порт 5432 и имя БД, отличное от urbansketch_migration_test. Runner создал собственный тестовый проект/концепцию и временные модели, затем очистил только их. Две восстановленные пользовательские модели не изменялись.

Прошли **19 PostgreSQL HTTP-тестов**, включая:

- Полный POST calculate по контрольным параметрам ТЗ; JSON-категории и итоги 150000000/250000000/100000000, ROI 66.6667 (66,67% при отображении), рентабельность 40%.
- Сохранение основных итогов, JSON-снимка и fingerprint: последующий GET читает current-снимок из новой request-scoped EF-сессии, повторный POST даёт тот же результат.
- not_calculated до первого расчёта, 404 отсутствующей модели, запрет произвольного тела calculate.
- stale после PUT цены/строительной площади и изменения исходных ТЭП тестовой концепции; повторный расчёт обновляет суммы.
- Очистка override и incomplete при неизвестной площади: выручка доступна, фиктивных общих затрат/прибыли нет; старый снимок не выдаётся как current.
- NULL ROI при нулевых затратах и NULL рентабельности при нулевой выручке без ошибки всего расчёта.
- Decimal overflow, storageRange и storageScale: HTTP 422, пять итогов и snapshot/hash не перезаписываются частично.
- Независимость моделей, корректное чтение/удаление собственных временных моделей, маскирование stale в прежнем GET/list CRUD.
- Детерминированный fingerprint при смене локали и масштаба decimal; реальные конкурирующие блокировки модели и концепции дают 409.

Исходные ТЭП и все поля обеих восстановленных моделей после тестов точно совпали с исходным снимком, включая overrides. Временные записи удалены, остались 1/2/2/0.

## Безопасные GET основной базы

Актуальная сборка backend запущена отдельным собственным процессом на свободном loopback-порту. Только для этого процесса основное PostgreSQL-подключение дополнено `default_transaction_read_only=on`. Пользовательские серверные процессы не завершались.

Выполнено 6 безопасных HTTP-запросов:

- GET финансовой модели для каждого из двух существующих id — 200, правильные id и принадлежность концепции.
- GET `/api/financial-models/{id}/calculation` для обеих моделей — 200, `state=not_calculated`, `isCurrent=false`, `result=null`.
- GET списка моделей для каждой из двух концепций — 200, ожидаемое количество.

POST calculate для существующих моделей основной БД **не запускался**. Тестовых моделей в основной базе не создавалось. Проверочный read-only процесс остановлен после запросов; User Secrets сохранены.
