## Цель и технологии

через уже реализованный REST API. Сохранены React/TypeScript/Vite, оформление
первого спринта, боковая навигация, типографика и адаптивная сетка.

Новые npm-пакеты, страницы и глобальные хранилища не добавлялись.

Backend, схема PostgreSQL, InitialCreate, тестовый JSON, пароли и User Secrets
не изменялись. Расчёты, денежные потоки и сравнение не реализовывались.

## Выбранная концепция и несколько моделей

Экран получает выбранный контекст из существующего useConceptSelection в App.
Показываются названия проекта и концепции. Для CRUD нужен conceptVariantId;
projectId остаётся частью общей пары выбора и определяет проект в исходном экране.
Без концепции форма не показывается, есть действие «К исходным данным».
Запросы с пустым/неверным Guid не отправляются.

При выборе концепции выполняется GET списка её моделей. Если список непуст,
первая модель открывается дополнительным GET по ID; другие доступны через select.
Порядок списка берётся из API. Подписи вида «Модель 1 · 78dc21da…7af8» используются
только для отображения: значение option и React key — полный серверный Guid.
Индекс не используется для загрузки, обновления или удаления.

При пустом списке показано сообщение и кнопка «Создать модель». У модели нет
пользовательского названия в действующей схеме, поэтому такое поле не добавлялось.
При смене концепции прежний список и параметры сразу скрываются.

## Точность денег и контракт JSON

Backend принимает и возвращает денежные поля именно числовыми JSON-токенами,
а не строками. Numeric(20,2) допускает до 18 цифр целой части и 2 дробных,
поэтому обычный JSON.parse → Number → JSON.stringify может потерять копейки.

В форме и TypeScript-представлении DTO денежные значения хранятся точным
десятичным текстом. Это адаптация транспортного numeric, не изменение API:

1. Ответ финансового API читается как текст.
2. Небольшой строгий JSON-парсер сохраняет числа объектами JsonNumber с исходным
   токеном, до преобразования в Number. Строки и объекты не могут выдать себя за числа.
3. Типы, Guid, обязательные поля и numeric-диапазоны проверяются; значения
   приводятся к канонической десятичной строке средствами строк/BigInt.
4. POST/PUT формируются только из разрешённых полей. Проверенные суммы вставляются
   как точные числовые токены без кавычек. ID/результаты/концепция в PUT не попадают.

Пример внутреннего значения: `"999999999999999999.99"`.
Его фрагмент на проводе: `"landCost":999999999999999999.99`.
Number/parseFloat для денежных сумм не используются. В Number переводится только
проверенный int32-срок; технические индексы строк также не являются деньгами.
Будущие nullable-результаты DTO читаются без потери точности, но не редактируются
и не отображаются как рассчитанные значения.

## Валидация

Все девять полей обязательны. Денежные значения неотрицательны, явно введённый
0 разрешён. Поддерживаются запятая и точка, а также корректные группы тысяч
через пробел, например 1 000 000,50. Начальные нули нормализуются.

В пользовательском вводе допускается максимум два дробных знака. Лишняя точность
не округляется: 1,001 отклоняется. Максимум — 999999999999999999,99, по схеме
numeric(20,2). Отрицательные суммы, NaN, Infinity, экспонента в поле ввода,
посторонние символы и неверные группы разрядов отклоняются.
При чтении корректного числового JSON экспоненциальная запись поддержана точно.

Срок — положительное целое int до 2147483647; произвольного бизнес-лимита нет.
Пустота не преобразуется в ноль. Ошибки привязаны к полям, aria-invalid и
aria-describedby помогают определить ошибочные элементы.

HTTP 400 ValidationProblemDetails читается по фактическому errors: строки
показываются возле соответствующих полей, ошибки body/контекста — в общей области.
Детали HTTP 500, стек и конфигурация сервера пользователю не передаются.
Клиентская проверка не заменяет серверную: backend не изменялся.

## Создание, открытие и редактирование

getFinancialModels/getFinancialModel используют существующие GET URL;
createFinancialModel — POST, updateFinancialModel — PUT,
deleteFinancialModel — DELETE. Используются общий базовый URL и Vite proxy.

После валидного POST экран ожидает подтверждённый HTTP 201 и корректный DTO.
Только затем появляется «Финансовая модель сохранена», серверный ID выбирается,
форма переходит в edit, значения становятся baseline, список обновляется GET.
Параметры не теряются, если сохранение отклонено. Если POST не подтверждён
из-за сети/повреждённого ответа, автоматического повтора нет; нужно сначала
обновить список, чтобы проверить возможную запись на сервере.

При выборе другой модели параметры очищаются и выполняется GET по полному Guid.
Ошибка чтения не открывает пустую форму под видом сохранённой модели: есть
сообщение и повтор загрузки. PUT отправляет полный набор девяти параметров,
без id, conceptVariantId и расчётных результатов. После HTTP 200 форма и список
обновляются подтверждёнными значениями.

При обновлении списка после уже подтверждённого сохранения ошибка списка
показывается отдельно: подтверждённая модель остаётся в локальном списке.

## Удаление

Перед DELETE используется явный native confirm. Для dirty-формы сообщение
дополнительно предупреждает о потере несохранённых изменений. Отмена не отправляет
запрос и не меняет форму. Успешный HTTP 204 удаляет запись из списка, очищает
текущий ID/форму и показывает «Финансовая модель удалена». Ошибка удаления
сохраняет запись в интерфейсе. Проект и концепция этим действием не удаляются;
backend использует уже существующую политику каскада дочерних потоков.

## Защита ввода и асинхронных состояний

useFinancialModels вызывается в App и сохраняет draft независимо от монтирования
экрана. Dirty сравнивается с подтверждённым baseline по значениям:
1000,00 и 1000.00 эквивалентны, пустота и 0 различаются.

Выбор другой модели, новый draft, переход на другой экран и смена
проекта/концепции проверяют canDiscard. При dirty требуется подтверждение;
при отмене данные/выбор/экран сохраняются. При согласии draft возвращается
к baseline перед переходом. Перед удалением dirty также учитывается.
Если изменений нет, подтверждение выхода не показывается.
beforeunload подключается только при dirty и удаляется после сохранения/сброса.
Окончательный показ браузерного диалога перезагрузки зависит от политики браузера.

Сохранение/удаление блокируют форму, выбор и уход до завершения операции.
Синхронный busy ref защищает даже от двух submit в одном пакете событий.
Мутации не отменяются переключением, поскольку отмена HTTP не гарантирует
откат уже выполняющегося серверного POST. Для чтения применяются AbortController,
ключ контекста и версия запроса; поздний ответ не заполняет другую модель
или концепцию, даже если транспорт игнорирует отмену.

## Ограничения и готовность спринта

Расчётов и реальных результатов пока нет. Остальные макетные экраны результатов
и сравнения не получили расчётную логику. Авторизация, новая схема и страницы
не добавлялись. Конкурентное редактирование следует текущему backend-контракту
без optimistic version/ETag. После неоднозначного сетевого исхода POST необходимо
сверить список перед повтором; автоматического повторного создания нет.

Функциональность второго спринта готова к итоговой проверке команды и оформлению
учебного отчёта. Для обычного запуска остаётся актуализировать backend на 5079.
Далее можно отдельно проектировать расчётный сервис и отображение результатов
третьего спринта; в рамках этой задачи он не начат.
