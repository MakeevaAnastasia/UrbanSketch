## Сопоставление схем

Исторические `database/schema.sql` и `database/erd.mmd` описывают семь таблиц
в единственном числе. В `docs/05_architecture.md` указаны три основные сущности
и связанные входы, распределения и результаты; отдельного утверждения о четырёх
физических таблицах в этом файле нет. Текущие четыре сущности и названия таблиц
заданы последующими заданиями спринта 2.

| Историческая таблица | Назначение | Текущее хранение |
|---|---|---|
| project | Проект | projects |
| concept_variant | ТЭП варианта | concept_variants |
| financial_model | Принадлежность модели и срок | financial_models |
| financial_input | Цены, затраты и строительные площади | financial_models; строительные площади в concept_variants |
| annual_allocation | Годовые доли затрат и выручки | cash_flows.expense_percent / revenue_percent |
| financial_result | Итоговые затраты, выручка, прибыль, коэффициенты | Nullable-поля financial_models |
| annual_cash_flow | Рассчитанные годовые потоки | Nullable-поля cash_flows |

Таким образом, три дополнительных выделенных хранилища (`financial_input`,
`annual_allocation`, `financial_result`) не требуют отдельных таблиц для
обязательной функциональности второго спринта. Ввод, сохранение и повторное
открытие параметров, проекты, варианты и несколько моделей на вариант
поддерживаются текущей структурой. Результаты и потоки можно хранить после
будущих расчётов, сохраняя null до расчёта.

Отличия, которые не следует скрывать:

- Имя, валюта и временные метки финансовой модели, дата расчёта, дата создания
  варианта из старого проекта не представлены текущими сущностями. Текущие
  задания их не требуют; валюта и версионирование не утверждены как обязательные.
- Строительные площади относятся к варианту, а не отдельной финансовой модели:
  разные строительные площади для моделей одного варианта сейчас не хранятся.
- Отдельные количества строящихся и продаваемых парковочных мест отсутствуют.
  Их разделение остаётся открытым вопросом первого спринта; текущим заданием
  предусмотрено одно ParkingSpaces.
- Исторические CHECK для непустых имён, неотрицательных входных значений и
  положительной длительности не перенесены в ранее созданный контекст.
  NOT NULL не запрещает пустое имя или отрицательное число. До реализации
  записи через API требуется предусмотреть валидацию по требованиям;
  миграция воспроизводит текущую модель и не расширяет её автоматически.
- Обязательные по текущей модели реализуемые площади и парковочные места
  не получают SQL DEFAULT 0. Необязательные ТЭП и результаты остаются nullable.

Блокирующего противоречия для текущей задачи подготовки первой миграции не
обнаружено; существующих данных, требующих переноса между схемами, нет.
Исторический SQL не следует выполнять вместе с новой миграцией.

## Артефакты и ограничения

В `backend/UrbanSketch.Financial.Api/Data/Migrations` созданы:

- `20261111075406_InitialCreate.cs`;
- `20261111075406_InitialCreate.Designer.cs`;
- `FinancialDbContextModelSnapshot.cs`.

Миграция содержит ровно четыре CreateTable и три CreateIndex в Up:

- projects → concept_variants → financial_models → cash_flows;
- четыре PK uuid и три обязательных FK с ON DELETE CASCADE;
- обычные индексы concept_variants(project_id), financial_models(variant_id);
- уникальный индекс cash_flows(financial_model_id, period_number);
- CHECK: period_number > 0, expense_percent и revenue_percent от 0 до 100.

FK variant_id не уникален, поэтому несколько финансовых моделей одного
варианта поддерживаются. Типы: integer; timestamp with time zone;
numeric(20,2) для денег, (18,2) для площадей, (7,4) для долей,
(12,4) для ROI и рентабельности.

`docs/sql/initial_create_review.sql` сформирован инструментом dotnet-ef
от 0 до InitialCreate. Кроме четырёх предметных таблиц он создаёт служебную
`__EFMigrationsHistory` и вставляет только запись о миграции.
В прямом SQL нет DROP, DELETE, UPDATE, TRUNCATE или ALTER.
Сгенерированный Down содержит четыре DropTable для явного отката;
он не входит в SQL применения и не выполнялся. Откат после появления
данных приведёт к их удалению.
