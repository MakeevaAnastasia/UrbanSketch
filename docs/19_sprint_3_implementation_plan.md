## 4. Решение по строительным площадям

| Вариант | ТЗ и независимость моделей | Данные, миграция и API | UI, точность и повторное открытие |
|---|---|---|---|
| Изменять ConceptVariant | Ручной ввод возможен, но меняет входы всех моделей концепции | Колонки уже есть; нужен новый write API концепции; смешивает исходный ТЭП и пользовательскую правку | Общий редактор, decimal(18,2), после открытия все модели увидят общую правку; понадобится массовая инвалидизация |
| Переопределения FinancialModel — рекомендуется | Выполняет §5.1 и изолирует модели | Две nullable колонки, расширение существующих DTO/POST/PUT; исходный ТЭП неизменен | Два поля в форме модели, точные строки ↔ decimal(18,2), сохранение с конкретной моделью |
| Только transient-площади в calculate | Формула возможна, но параметры не воспроизводятся после открытия | Миграция не нужна; тело calculate содержит площади | Ручной повторный ввод, риск расхождения результатов и параметров; не соответствует полному сценарию сохранения |

Добавить `ConstructionResidentialAreaOverride`, `ConstructionCommercialAreaOverride` в FinancialModel (`decimal?`, `numeric(18,2)`). JSON: `constructionResidentialAreaOverride`, `constructionCommercialAreaOverride`. Effective = override ?? исходная строительная площадь ConceptVariant; **0 является заданным значением**. Никогда не брать реализуемую площадь как fallback. Null override означает «использовать исходную»; если обе величины null — модель сохраняется как неполная, расчёт блокируется с ошибкой соответствующего поля. Даже при нулевой ставке неизвестную строительную площадь не считать нулём.

В UI показывать отдельно исходную площадь, переопределение и используемое значение, действие «Использовать исходную». Пустой ввод даёт null; отрицательные и значения с ненулевыми знаками после сотых запрещены; верхняя граница 9999999999999999.99. Не вводить правило construction ≥ sale: оно не задано ТЗ. Расчёт выручки всегда берёт реализуемые площади исходной концепции.

## 5. Формулы и точность

Обозначения: Bж/Bк — effective строительные площади; Sж/Sк — реализуемые; N — ParkingSpaces; Cж/Cк/Cп — ResidentialConstructionCost/CommercialConstructionCost/ParkingCost; Pж/Pк/Pп — ResidentialSalePrice/CommercialSalePrice/ParkingSalePrice; L/D — LandCost/AdditionalCosts.

```text
HousingCosts = Bж × Cж; CommercialCosts = Bк × Cк; ParkingCosts = N × Cп
TotalCosts = HousingCosts + CommercialCosts + ParkingCosts + L + D
HousingRevenue = Sж × Pж; CommercialRevenue = Sк × Pк; ParkingRevenue = N × Pп
TotalRevenue = HousingRevenue + CommercialRevenue + ParkingRevenue
Profit = TotalRevenue − TotalCosts
Roi = TotalCosts == 0 ? null : Profit / TotalCosts × 100
SalesProfitability = TotalRevenue == 0 ? null : Profit / TotalRevenue × 100
```

Все вычисления — C# decimal, без double/float и клиентского Number. Null обязательного входа — ошибка, нулевые площади/цены/парковки допустимы, отрицательная прибыль и проценты допустимы. Срок сохраняется и валидируется, но не участвует в этих итогах. Не добавлять повторно землю к объединённым расходам примера.

Предложение по хранению: расширить три существующих денежных итога до `numeric(22,4)` — сохранить 18 целых разрядов и точные четыре дробных разряда произведений двух входов с сотыми. Компоненты расходов/доходов считать в памяти; в этом спринте не добавлять их колонки. Существующие пять полей остаются единственным хранилищем итогов.

Произведения максимально допустимых входов могут превысить decimal, даже если каждый вход валиден. До умножения проверять допустимость произведения и будущего итога; при превышении 999999999999999999.9999 либо ёмкости decimal возвращать контролируемую ошибку `calculation`, не 500 и не частичную запись. При суммировании проверять диапазон. Нельзя полагаться только на checked: decimal способен уменьшать scale при больших произведениях. Проверка верхней границы результата до операции исключает такое незаметное уменьшение для принятого диапазона.

Проценты хранить в существующем `numeric(12,4)` с **явным** `decimal.Round(value, 4, MidpointRounding.AwayFromZero)` после вычисления; максимум модуля 99999999.9999. Выход за диапазон — ошибка всего расчёта, не null. Это предложенная политика точности, которую нужно явно описать в API. UI форматирует до 2 знаков тем же правилом на десятичной строке: ROI 66.6667 → 66,67%. Денежные итоги показывать с сохранением до 4 знаков, без скрытого округления до копеек. Промежуточные суммы не округлять.

## 6. Структура будущего сервиса

Создать в backend `Calculations/`:

## 9. Сохранение, миграция и актуальность

Новая миграция, предлагаемое имя `AddFinancialCalculationInputs`: две nullable override-колонки numeric(18,2), nullable `CalculationInputHash` (строка 64 hex-символа), расширение трёх денежных итогов до numeric(22,4); обновить EF snapshot и Designer новой миграции. InitialCreate и её Designer не редактировать. Existing модели не удалять; defaults не заполняют неизвестные площади. Старые результаты без hash не считать актуальными. Перед downgrade проверить дробные разряды: обратное сужение может округлить данные, автоматический downgrade на пользовательской БД не выполнять.

`calculationStatus`: `notCalculated` при hash=null; `stale` при несовпадении hash с текущими входами/версией; `calculated` при совпадении. Наличие/отсутствие Roi не является признаком завершённости. Для notCalculated/stale API маскирует пять итогов как null, чтобы старый клиент не показал устаревшие числа. GET ничего не записывает.

При изменении параметров/overrides через PUT очищать результаты/hash в той же записи. При изменении исходных ТЭП fingerprint обнаруживает устаревание даже без write API концепции; все GET и списки должны читать текущие входы. Изменения JSON не импортировать автоматически. Сам исходный ТЭП/seed остаётся неизменным.

Calculate берёт блокировки строки модели и строки концепции в одной транзакции до чтения входов (единый порядок: концепция, затем модель; после блокировки повторно проверить связь). PUT модели конфликтует с блокировкой модели; изменение концепции — с блокировкой концепции. Альтернатива при реализации допустима только с эквивалентной проверкой concurrent writes. Результат и hash записываются вместе; при исключении rollback, прежние данные не повреждаются. Повторный calculate с неизменными входами даёт те же итоги и не создаёт новых моделей. После сетевого сбоя можно перечитать GET и повторить расчёт существующего id.

## 12. Риски, ограничения и готовность

- Git-зависимость: второй спринт ещё отсутствует в main. Это препятствие созданию корректной ветки разработки; расчёты не начинать до разрешения зависимости и отдельной задачи пользователя.
- Рекомендации по overrides и numeric(22,4) являются предложениями этого плана. Их нужно принять при постановке реализации; точность процентов/отображения документировать явно, а не оставлять PostgreSQL.
- DATA-01 закрывается задачами 1/4, DATA-02 — задачей 4, DATA-03 — проверками обязательных входов задачи 2. Неизвестные нефинансовые ТЭП остаются неизвестными.
- DEMO-01: старый процесс 5079 ранее давал 404; перед проверкой подтвердить актуальность API. Не завершать чужие процессы автоматически. Health не доказывает доступность БД.
- Нет авторизации; блокировки calculate не заменяют защиту от потери несохранённых изменений между двумя клиентами. Полный ETag/optimistic concurrency остаётся отдельной задачей.
- Оригинальное ТЗ шире этого спринта; годовые потоки/сравнение/экспорт не являются условиями завершения спринта 3. `cash_flows` не заполнять фиктивными данными.
- В этой подготовке PostgreSQL не читалась и не изменялась, миграции/JSON/исходный код не менялись, модели не удалялись, push/commit/merge не выполнялись. Проверка схемы — по исходникам и приёмке, не аудит текущего тома БД.

План достаточен для постановки первого этапа реализации; фактический старт заблокирован отсутствием спринта 2 в main. Следующее действие — отдельное решение об объединении PR, безопасная подготовка ветки и новая задача на программные изменения.
