Дата: 24 ноября 2026 года, Europe/Moscow. Ветка: `feature/sprint-3-financial-calculations`.

## Цель и объём

Добавлен ввод, сохранение, редактирование и очистка двух строительных площадей финансовой модели через существующий CRUD API. Это продолжение backend-этапа [docs/20](20_construction_area_overrides.md) после применения миграции, подтверждённого в [docs/21](21_construction_area_migration_result.md).

Строительные площади используются будущим расчётом затрат; реализуемые площади концепции предназначены для выручки. Автоматического приравнивания нет. Формулы, годовые потоки, экран результатов, сравнение и CSV в этой задаче не реализовывались. Существующие миграции, серверная валидация, тестовый JSON и исходные ТЭП не изменены.

## Форма и источники значений

Блок «Строительные площади» содержит:

- «Строительная жилая площадь, м²» — `constructionResidentialAreaOverride`.
- «Строительная коммерческая площадь, м²» — `constructionCommercialAreaOverride`.

Используются существующие поля `type="text"` с `inputMode="decimal"`, стили, сетка, кнопки и боковая навигация. Девять прежних финансовых параметров сохранены. Под блоком поясняется, что строительные площади могут отличаться от реализуемых и что пустое поле означает отсутствие пользовательского переопределения.

Новая модель начинает с двух пустых полей. При открытии модели null превращается в пустую строку, 0 — в `0,00`, положительное число — в точную строку с запятой. Сохранённые параметры остальных полей не меняются.

Под каждым полем отображается источник:

1. Валидный непустой override, включая 0: «Используется пользовательское значение».
2. Пустой override и известная строительная площадь ConceptVariant: «Используется исходная площадь концепции: X м²».
3. Оба значения отсутствуют: «Строительная площадь не задана».

При некорректном вводе источник не объявляется действующим — предлагается проверить площадь. Пока ТЭП загружаются или недоступны, показывается соответствующее состояние, а не ложное сообщение об отсутствии исходной площади. Проверяется принадлежность источника текущей концепции.

Это отображение повторяет приоритет backend `ConstructionAreaResolver`, но не выполняет финансовых вычислений. Исходные площади никогда не копируются в overrides автоматически. Существующий `useConceptSelection` с отменой/защитой от устаревших ответов сохранён.

## Точность и клиентская валидация

Площади в editable draft — строки; валидные значения запросов/ответов внутри клиента — `string | null`. JSON API при этом по-прежнему использует **числа**, не числовые строки.

Валидация `normalizeArea`:

- Пустой ввод/пробелы → null.
- Ноль допустим и отличается от null.
- Запятая и точка принимаются как десятичный разделитель; допускаются корректно сгруппированные пробелами тысячи по существующим соглашениям денежных полей.
- Только неотрицательные числа, до двух дробных знаков, максимум `9999999999999999.99` (numeric(18,2)).
- Отрицательные значения, лишние дробные знаки, экспонента в ручном вводе, NaN/Infinity и посторонние символы отклоняются.
- Округления нет: значение либо представимо точно, либо выдаётся ошибка.

Для числовых wire-токенов используются существующие `parseExactJson`, `JsonNumber`, `exactDecimal`. Строительные площади не преобразуются через JavaScript Number. Для двух исходных строительных площадей ConceptVariant также добавлен точный decoder: исходный токен восстанавливается в строку до использования в UI, поэтому максимум numeric(18,2) сохраняет сотые. Прежнее представление остальных ТЭП этим этапом не перерабатывалось.

Клиентские ошибки выводятся рядом с полем, связаны через aria-describedby и aria-invalid. Новые имена включены в существующий список полей для сопоставления ValidationProblemDetails. Ошибка сервера body остаётся общей ошибкой формы.

## Сохранение и очистка

Маршруты не менялись: POST/GET/PUT `/api/financial-models`, GET списка `/api/concepts/{id}/financial-models`, существующий DELETE модели.

Оба новых поля передаются явно при сохранении текущим UI. Пример фрагмента полного тела запроса:

```json
{
  "constructionResidentialAreaOverride": 1000.25,
  "constructionCommercialAreaOverride": null
}
```

Это фрагмент: девять прежних финансовых параметров обязательны; POST дополнительно включает conceptVariantId. Для serializing чисел используется whitelist и сборка точных JSON-токенов, без JSON.stringify(Number(decimal)).

Очистка поля отправляет явный null. Он не удаляется из тела запроса: backend различает отсутствие поля старого клиента и намеренную очистку. При POST/PUT успех показывается только после подтверждённого ответа. После POST выполняется GET по серверному id и обновляется список моделей. Если POST уже успешен, но GET не удался, повторный POST блокируется до обновления списка; браузерный тест подтверждает отсутствие дубликата и возможность открыть уже созданную модель.

При PUT остальные финансовые параметры отправляются вместе с двумя фактическими overrides, не сбрасывая их. После перезагрузки модель можно выбрать по устойчивому серверному id и восстановить через GET. Автоматическое запоминание выбранного id между загрузками страницы не добавлялось.

## Несохранённые изменения и запросы

Оба поля входят в общий FinancialField/FinancialDraft и семантический dirty-check. Пустое значение и ноль различаются, запись `1,20` равнозначна `1.2`.

Используется существующая защита при переключении модели/концепции/экрана, создании новой модели и удалении; beforeunload предупреждает при перезагрузке/закрытии. Сохранение обновляет baseline и снимает dirty. Пока выполняется сохранение, поля и опасные действия блокируются. Для GET модели сохранены AbortController, версия запроса и проверка контекста концепции — поздний ответ не перезаписывает текущую форму.

## Проверка реального приложения и PostgreSQL

Использованы собственные экземпляры актуального backend **127.0.0.1:5196** и Vite **127.0.0.1:5176**, proxy направлен на этот backend. Прежние процессы, включая возможный сервер 5079, не завершались. Существующая локальная база подтверждена по конфигурации предыдущего этапа и активному контейнеру; непосредственно проверены история обеих миграций и начальное количество моделей **2**.

В реальном браузере выполнен сценарий Концепции А:

1. Создана собственная временная модель с девятью контрольными параметрами, землёй 14000000, дополнительными расходами 10000000 и площадями 1000/200.
2. После POST/GET браузер перезагружен, временная модель выбрана по её id: площади 1000/200 восстановлены.
3. Площади изменены на 1200/240, сохранены через PUT, модель повторно открыта: значения сохранились.
4. Жилая площадь очищена; GET вернул residential override=null, commercial override=240. Остальные параметры, включая landCost=14000000, сохранены.
5. Временная модель удалена через UI; GET её id вернул 404. При сбоях harness выполняет cleanup только своих известных id.
6. Ответы списков моделей и ТЭП обеих концепций до/после цикла совпали. Дополнительно прямой PostgreSQL JSONB-снимок всех четырёх таблиц сопоставлен с сохранённым снимком предыдущего этапа: все прежние значения и id совпали. Оба overrides двух существующих моделей по-прежнему NULL. Итог: 1 проект, 2 концепции, 2 модели, 0 потоков.

Независимость моделей дополнительно проверена браузерным сценарием с двумя моделями одного mock-концепта: сохранение и очистка первой не меняет площади второй. Backend также имеет отдельные проверки независимости. Две существующие пользовательские модели не использовались как тестовые записи для редактирования.
