## Цель и технологии

Цель — подготовить локальную базу UrbanSketch.pro к хранению проектов,
вариантов концепций, финансовых параметров и денежных потоков во втором спринте.

Использованы ASP.NET Core / .NET 10, Entity Framework Core и dotnet-ef
10.0.15, Npgsql 10.0.3, PostgreSQL 17.11 в Docker Compose.
Контекст — FinancialDbContext; миграция — `20261111075406_InitialCreate`.

## Как настроено подключение

Проблема предыдущего этапа решена: ключ `ConnectionStrings:DefaultConnection`
сохранён в .NET User Secrets существующего проекта. Использован уже заданный
UserSecretsId, изменение .csproj не понадобилось.

Учётные данные взяты из локального infrastructure/.env, сверены в памяти
с разрешённой конфигурацией Docker Compose и переменными работающего контейнера.
Пользователь и пароль PostgreSQL не менялись. JSON передан команде
`dotnet user-secrets set` через стандартный ввод, без временных файлов с секретами
в проекте и без пароля в аргументах команд. Секрет хранится вне репозитория.

Подтверждённое подключение: **127.0.0.1:5432, база urbansketch_financial**.
Контейнер infrastructure-postgres-1 работает и имеет статус healthy.

Проверка через стандартную конфигурацию ASP.NET Core в Development подтвердила
успешную авторизацию. Идентификатор кластера из pg_control_system() совпал
при подключении из приложения и через psql внутри контейнера. Это подтверждает,
что приложение обращается именно к локальному серверу проекта.

ASPNETCORE_ENVIRONMENT и DOTNET_ENVIRONMENT задавались как Development только
для процесса запуска EF CLI и восстанавливались после команд. Глобальные
переменные Windows не изменялись. Прикладной Program.cs не изменён;
автоматическое применение миграций при старте не добавлено.

## Созданные таблицы и связи

В схеме public подтверждены ровно пять таблиц:

| Таблица | Назначение | Число строк после применения |
|---|---|---:|
| projects | Проекты | 0 |
| concept_variants | ТЭП вариантов концепций | 0 |
| financial_models | Параметры и будущие результаты расчётов | 0 |
| cash_flows | Годовые доли и будущие денежные потоки | 0 |
| __EFMigrationsHistory | История EF Core | 1 |

У каждой предметной таблицы первичный ключ id типа uuid. Проверены связи:

- concept_variants.project_id → projects.id;
- financial_models.variant_id → concept_variants.id;
- cash_flows.financial_model_id → financial_models.id.

Все три внешних ключа обязательные, имеют ON DELETE CASCADE и поддерживают
связи один ко многим. Индекс variant_id не уникален: несколько финансовых
моделей одного варианта разрешены.

## Индексы и ограничения

В системных каталогах подтверждены четыре PK-индекса и три дополнительных:

- IX_concept_variants_project_id;
- IX_financial_models_variant_id;
- уникальный ux_cash_flows_financial_model_id_period_number
  по (financial_model_id, period_number).

Все семь предметных индексов валидны. Проверены определения CHECK:

- ck_cash_flows_period_number: period_number > 0;
- ck_cash_flows_cost_share: expense_percent от 0 до 100;
- ck_cash_flows_revenue_share: revenue_percent от 0 до 100.

Все 42 столбца предметных таблиц сопоставлены с метаданными EF Core:
имена, PostgreSQL-типы, точность и nullable совпадают. Проверены uuid, integer,
timestamp with time zone, numeric(20,2) для денег, numeric(18,2) для площадей,
numeric(7,4) для долей, numeric(12,4) для ROI и рентабельности.
Необязательные ТЭП, строительные площади и результаты остаются nullable.

Исторические CHECK непустых имён, неотрицательных входных величин и положительной
длительности отсутствуют в текущей модели, как отмечено в аудите этапа 10.
Применение воспроизводит подготовленную миграцию; перед загрузкой JSON потребуется
валидация входных данных. Финансовые расчёты здесь не выполнялись.

## История и повторное обнаружение

В __EFMigrationsHistory ровно одна запись:

- MigrationId: 20261111075406_InitialCreate;
- ProductVersion: 10.0.15.

`dotnet ef migrations list` видит InitialCreate как применённую, без отметки
Pending. GetPendingMigrations() возвращает пустой список.
`dotnet ef migrations has-pending-model-changes` сообщает, что изменений
модели после последней миграции нет. Повторное применение DDL не запускалось.

## Проверки, ошибки и предупреждения

Использованы docker compose ps, SELECT через psql, а также запросы через
подключение приложения к pg_class, pg_namespace, pg_attribute, pg_constraint,
pg_index и __EFMigrationsHistory. Проверка данных, столбцов, ограничений,
индексов и истории после применения проходила внутри READ ONLY.

Сборка backend: **0 ошибок, 0 предупреждений**. Работающий backend не завершался.

При первичном чтении ещё отсутствовавшей __EFMigrationsHistory EF CLI вывел
Failed executing DbCommand для SELECT истории. После этого штатно создал историю,
применил InitialCreate и завершился с кодом 0. Последующее чтение истории
успешно; это сообщение не означает неуспешное применение миграции.

Первый вспомогательный вызов проверки идентификатора Docker не получил значение
из-за передачи SQL через командную строку. Запрос повторён безопасно через stdin;
идентичность сервера подтверждена до применения миграции.
