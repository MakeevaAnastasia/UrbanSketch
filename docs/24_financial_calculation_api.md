## Маршруты и HTTP-семантика

| Маршрут | Поведение |
|---|---|
| POST `/api/financial-models/{id}/calculate` | Загрузить сохранённые входы, рассчитать, сохранить только полный совместимый результат |
| GET `/api/financial-models/{id}/calculation` | Получить последний успешный сохранённый расчёт, проверив актуальность; вычисления не запускаются |

POST не принимает тело, включая JSON `{}`: при переданном теле возвращается HTTP 400 ValidationProblemDetails. Нужные входы предварительно сохраняются обычным POST/PUT модели. Отсутствующий id — 404; некорректный Guid не соответствует маршруту и также даёт 404.

Примеры запросов:

```http
POST /api/financial-models/{id}/calculate
Accept: application/json
```

```http
GET /api/financial-models/{id}/calculation
Accept: application/json
```

Ответ обёрнут в `CalculationResponse(State, IsCurrent, Result)`. State в JSON:

| state | HTTP | result и сохранение |
|---|---|---|
| not_calculated | GET 200 | null; успешный снимок ещё не сохранён, GET ничего не вычисляет |
| current | GET/POST 200 | Полный сохранённый результат; isCurrent=true |
| stale | GET 200 | null; сохранённый hash не совпадает с текущими входами; старые числа не выдаются за текущие |
| incomplete | POST 200 | Частичный результат, missingInputs; isCurrent=false; запись не выполняется |
| error | POST 422 | Ошибки вычисления или несовместимость с PostgreSQL; isCurrent=false; запись не выполняется |

Неожиданные внутренние/инфраструктурные ошибки обрабатывает существующий безопасный ProblemDetails 500 без раскрытия деталей. Конкурентные блокировки/сериализация/дедлок возвращают ProblemDetails **409** с предложением повторить расчёт. Null-проценты из-за нулевого знаменателя не превращают корректный расчёт в ошибку.

Полный пример ответа для §9 ТЗ:

```json
{
  "state": "current",
  "isCurrent": true,
  "result": {
    "status": "complete",
    "costs": {
      "residential": 100000000, "commercial": 16000000,
      "parking": 10000000, "land": 14000000, "additional": 10000000
    },
    "revenue": {
      "residential": 200000000, "commercial": 30000000, "parking": 20000000
    },
    "totalCosts": 150000000, "totalRevenue": 250000000,
    "profit": 100000000, "roi": 66.6667, "salesProfitability": 40,
    "missingInputs": [], "errors": [], "persistenceIssues": [],
    "canPersistToCurrentSchema": true
  }
}
```

Числа JSON выдаются серверным decimal-сериализатором, не строками и не double. Десятичный scale записи может различаться без изменения значения. Существующий frontend lossless-клиент совместим с прежними CRUD numeric(20,2)/(12,4); новый маршрут потребует отдельного подключения интерфейса. React в этой задаче не менялся.

## Хранение и миграция

Повторно использованы пять существующих полей FinancialModel: TotalCosts, TotalRevenue, Profit (`numeric(20,2)`), Roi/SalesProfitability (`numeric(12,4)`). Дублирующая таблица результатов не создаётся.

Добавлены два nullable-поля без defaults:

| Поле | PostgreSQL | Содержимое |
|---|---|---|
| CalculationInputHash | calculation_input_hash varchar(64) | SHA-256 нормализованных входов и версии алгоритма |
| CalculationSnapshot | calculation_snapshot text | Структурированный JSON всего CalculationResult, включая категории затрат/выручки |

JSON хранится как text: десятичные токены не проходят приближённые типы, сериализатор/десериализатор общий с endpoint. Прямое SQL-редактирование снимка не поддерживается. Снимок и пять денежных показателей записываются вместе в одной транзакции одной модели. Параметры, overrides, исходные ТЭП и другие финансовые модели не изменяются.

Миграция: **20261124075506_AddSavedFinancialCalculations**. Up добавляет ровно два nullable-столбца; прежняя точность numeric не меняется. Down стандартно удаляет только новые столбцы и теряет снимки; его нельзя считать недеструктивным откатом сохранённых результатов.

SQL: [sql/add_saved_financial_calculations.sql](sql/add_saved_financial_calculations.sql). Аудит Up-SQL: START TRANSACTION; два ALTER TABLE ADD; INSERT в __EFMigrationsHistory; COMMIT. Нет DROP, DELETE, UPDATE пользовательских строк, сужения numeric или пересоздания таблиц. Для старых моделей поля будут NULL, состояние not_calculated. Старые ненулевые итоги без подтверждённого hash не считаются текущими.

Основная локальная БД **не мигрировалась**. SQL успешно исполнен через EF только на отдельной PostgreSQL; прежние строки сохранены.

## Неполные расчёты, точность и ошибки

Существующий resolver используется внутри FinancialCalculationService: override → строительная площадь концепции → null. Неизвестность не превращается в ноль или реализуемую площадь. При отсутствии площади сервер возвращает неполный CalculationResult, включая достоверную выручку; TotalCosts/Profit/коэффициенты, зависящие от неизвестных затрат, null. Старый снимок не перезаписывается неполным результатом.

GET возвращает только последний успешный снимок или его отсутствие/устаревание. Последний неуспешный POST не сохраняется как отдельная история попыток: например, после изменения входов и incomplete-POST GET останется stale, либо not_calculated, если успеха никогда не было. Это явное решение — никаких скрытых расчётов на GET.

Проверка CanPersistToCurrentSchema **обязательна** перед записью. DecimalOverflow и invalidInput присутствуют в Errors; storageRange/storageScale — в PersistenceIssues. Все эти ожидаемые ошибки дают структурированный 422, не 500. Неполный/ошибочный POST не меняет ни snapshot/hash, ни одно из пяти старых значений.

Субкопеечные результаты не округляются ради записи: numeric(20,2) не принимает их в этом API, возвращается storageScale. Большой точный результат вне numeric-диапазона также не сохраняется. Это сохраняет прежний CRUD-контракт и не расширяет схему без отдельного решения. Возможное увеличение трёх итогов до numeric(22,4) остаётся предложением docs/19/23 для будущего согласования; в этой миграции его нет. Проценты по-прежнему вычисляются до 4 знаков AwayFromZero; ROI 66.6667 отображается как 66,67% при двух знаках.

## Fingerprint и актуальность

CalculationFingerprint включает версию `financial-v1-percent4-away-exact`, восемь финансовых сумм, срок, оба overrides, обе исходные и эффективные строительные площади, реализуемые площади и ParkingSpaces. Неучаствующие информационные ТЭП не включены. Включение исходной строительной площади даже при активном override и срока даёт консервативную инвалидизацию: любое изменение этих сохранённых входов требует повторного расчёта.

Порядок полей фиксирован; decimal сериализуется `G29` с InvariantCulture, null явно отличается от 0; поля разделены `|`, строковых пользовательских значений в наборе нет. SHA-256 возвращается 64 hex-символами. 1.0 и 1.00 имеют одинаковый hash независимо от локали. Изменение константы версии алгоритма инвалидирует прежние результаты.

На GET расчёта и обычных GET/list моделей читается текущая связанная концепция и пересчитывается **только hash**, не финансовые показатели. Совпадение hash и наличие снимка означают current. При несовпадении — stale. PUT сохраняет прежний исторический снимок/hash, но новые входы делают его stale. Обычный CRUD не добавляет новые обязательные поля ответа и маскирует пять устаревших итогов как null; идентификаторы, остальные поля и маршруты сохранены.

Таким образом, изменение ТЭП напрямую в БД тоже обнаруживается при следующем чтении. Проверка только updated_at модели не используется. Если все входы явно возвращены к прежним нормализованным значениям, сохранённый детерминированный результат снова допустим как current.

## Атомарность и конкурентность

POST работает в транзакции. На PostgreSQL после определения связи выполняется блокировка **сначала концепции, затем модели** через SELECT FOR UPDATE NOWAIT. После блокировок проверяется, что модель по-прежнему принадлежит найденной концепции. Чтение входов, вычисление, сохранение snapshot/hash/итогов и commit происходят под этими блокировками.

Параллельный PUT или изменение исходной концепции не могут изменить используемые строки во время вычисления/сохранения. Если писатель уже удерживает блокировку — calculate получает 409. Если писатель продолжит после commit расчёта, новое значение входов сделает результат stale при последующем чтении. Удаление модели после блокировки ждёт завершения транзакции; удалённая до блокировки модель даёт 404. Прямую смену связи при конкурентном SQL обнаруживает повторная проверка conceptId.

Обрабатываются SQLSTATE 55P03 (lock_not_available), 40001 (serialization_failure), 40P01 (deadlock_detected), включая обёртки EF/Npgsql. В изолированной PostgreSQL установлено, что Npgsql заворачивает 55P03 в InvalidOperationException; обработчик ищет только перечисленные SQLSTATE в цепочке исключений. После отказа транзакция откатывается при освобождении, частичной записи нет. Неизвестные исключения не выдаются за concurrency-конфликт.

Для SQLite-тестов остаётся транзакция без PostgreSQL-специфичных row locks. Проверка реальной конкурентности выполнена отдельно на PostgreSQL. Это не полноценный optimistic concurrency/ETag для редактирования черновиков: предотвращение потери изменений между двумя PUT остаётся отдельной задачей.

## Безопасное последующее применение и ограничения

Основная миграция — отдельный этап. До него нельзя запускать этот обновлённый backend против старой основной схемы: запросы FinancialModel теперь используют новые поля.

Перед применением: подтвердить локальную целевую БД и историю, создать свежий custom pg_dump вне Git и проверить восстановлением, просмотреть Up-SQL, сверить исходные записи, запланировать блокировку ALTER TABLE, затем по отдельному разрешению применить проверенную миграцию. После применения повторить проверку схемы/истории/данных и read-only GET. Не запускать downgrade без сохранения снимков.

JSON-снимок хранится без DB CHECK на структуру; корректность обеспечивается единственным серверным путём записи. Прямое стороннее редактирование snapshot/hash не поддерживается. История успешных версий и неудачных попыток не ведётся. Крупные несовместимые итоги остаются ошибкой сохранения, а не поводом автоматически менять numeric. Авторизация и полный ETag не добавлены. GET не записывает и не рассчитывает финансовые показатели.

React, новые экраны, потоки, сравнение и CSV не реализовывались. Commit, push и переключение ветки не выполнялись. Новая миграция к основной PostgreSQL **не применена**.
