# Пользовательские строительные площади финансовой модели

Дата: 24 ноября 2026, Europe/Moscow. Ветка: `feature/sprint-3-financial-calculations`.

## Назначение и границы

ТЗ §5.1 допускает ручной ввод строительных площадей при их отсутствии в ТЭП. Реализуемые площади предназначены для выручки, строительные — для затрат. Их равенство нельзя предполагать автоматически. В демо-концепциях строительные площади неизвестны. Переопределения принадлежат FinancialModel, чтобы разные модели одной концепции могли использовать разные предположения, сохраняя исходный ConceptVariant и JSON.

Основание: оригинальное ТЗ, план-график (спринт 3: 16–27 ноября), docs/17–19 и текущие EF/CRUD-соглашения. Эта задача реализует только хранение, API, разрешение площадей и подготовку миграции. React, формулы и экран результатов не изменены. Из широкого плана docs/19 здесь не реализованы fingerprint, расширение точности результатов и calculate endpoint. В отличие от первоначального предложения docs/19, отсутствие нового поля в PUT **сохраняет** прежнее значение — это уточнение текущей задачи для совместимости старых клиентов.

## Поля и определение используемой площади

| FinancialModel / JSON | PostgreSQL | Тип |
|---|---|---|
| `ConstructionResidentialAreaOverride` / `constructionResidentialAreaOverride` | `construction_residential_area_override` | nullable decimal / numeric(18,2) |
| `ConstructionCommercialAreaOverride` / `constructionCommercialAreaOverride` | `construction_commercial_area_override` | nullable decimal / numeric(18,2) |

Нет default 0, оба значения могут быть NULL. Исходные поля ConceptVariant не изменены.

Единая точка разрешения для будущего калькулятора — `ConstructionAreaResolver.Resolve(FinancialModel model, ConceptVariant concept)`. Возвращает `EffectiveConstructionAreas` с nullable `ResidentialArea` и `CommercialArea`:

1. Переопределение модели, если задано, включая настоящий 0.
2. Исходная строительная площадь соответствующей категории ConceptVariant.
3. Null, если неизвестны обе величины.

Реализуемые ResidentialArea/CommercialArea концепции не используются как fallback. Resolver принимает явно загруженную концепцию, поэтому не зависит от lazy loading. Не добавляются вычисляемые EF-колонки. Исходные ТЭП не записываются resolver-ом.

## CRUD и семантика PUT

Существующие маршруты сохранены:

- POST `/api/financial-models` принимает два необязательных поля. Пропуск или явный null создаёт NULL; число сохраняется.
- GET `/api/financial-models/{id}` и GET `/api/concepts/{id}/financial-models` возвращают оба сохранённых переопределения числами JSON либо null.
- PUT `/api/financial-models/{id}` по-прежнему требует все прежние финансовые параметры, но каждое новое поле обрабатывает независимо:

| Вход PUT | Поведение |
|---|---|
| Поле отсутствует | Сохранить прежнее переопределение |
| Поле равно null | Очистить переопределение |
| Поле равно числу | Заменить переопределение, включая 0 |

В базовом Request используются nullable decimal с init-setter и отдельными `[JsonIgnore]` признаками присутствия. Десериализация вызывает setter только для переданного поля; метод Apply меняет площадь только при установленном признаке. Это не превращает весь PUT в PATCH: прежние денежные поля и срок остаются обязательными.

Например, к существующему полному телу PUT можно добавить `"constructionResidentialAreaOverride":1000.25` для замены или `"constructionResidentialAreaOverride":null` для очистки. Если добавить только жилую площадь, коммерческая останется прежней. Передача результатов, id или смена conceptVariantId по-прежнему запрещены действующей валидацией. Идентичность модели и её связь с концепцией не меняются. DELETE не расширяется.

Ответы содержат сохранённые overrides, не effective-площади. Для будущих вычислений следует использовать resolver. Nullable финансовые результаты пока не рассчитываются, новый маршрут calculate не добавлен.

## Валидация и точность

`ConstructionAreaJsonConverter` адаптирует существующий точный разбор денежного токена к площади numeric(18,2). Property-level converter применяется только к новым полям, существующая денежная обработка не ослаблена.

- Null допустим; 0 допустим; отрицательные площади запрещены.
- Максимум: `9999999999999999.99`, до 16 целых и 2 значащих дробных разрядов.
- Проверяется исходный JSON-токен до преобразования в decimal: недопустимое значение не может незаметно округлиться или исчезнуть до нуля.
- Точная научная запись и незначащие конечные нули допустимы по существующим соглашениям: `1.2300e2` = 123. Ненулевой третий дробный знак запрещён.
- Строки, boolean, массивы, объекты, NaN/Infinity, переполнение и дробный underflow отклоняются. Повторяющиеся и неизвестные JSON-поля также запрещены.
- Произвольные деньги и площади через double/float не проходят.
- Ошибки возвращаются как HTTP 400 `ValidationProblemDetails`; синтаксис/токен — ошибка body, бизнес-ограничения площади — ошибка соответствующего поля. Проверка выполняется до Apply/SaveChanges, поэтому некорректный PUT не сохраняет часть входов.

## Миграция и SQL для проверки

Создана `20261124065820_AddFinancialModelConstructionAreaOverrides` с Designer и обновлением `FinancialDbContextModelSnapshot`.

Up содержит ровно два AddColumn в `financial_models`: nullable numeric(18,2), без default. Не меняются старые поля модели, projects и concept_variants. У старых строк новые значения будут NULL. InitialCreate и исходный seed не изменены. Down стандартно удаляет **только эти новые столбцы** и теряет введённые overrides; откат нельзя выполнять без предварительного сохранения этих данных.

Предварительный SQL: [sql/add_financial_model_construction_area_overrides.sql](sql/add_financial_model_construction_area_overrides.sql). Он содержит START TRANSACTION, два ALTER TABLE ADD, INSERT служебной записи в `__EFMigrationsHistory`, COMMIT. Нет DROP, DELETE, UPDATE существующих строк или пересоздания таблиц. Скрипт предназначен для применения один раз поверх InitialCreate, не является идемпотентным.

Команды подготовки, выполненные без применения к БД:

```powershell
dotnet ef migrations add AddFinancialModelConstructionAreaOverrides --project backend/UrbanSketch.Financial.Api --output-dir Data/Migrations
dotnet ef migrations script 20261111075406_InitialCreate AddFinancialModelConstructionAreaOverrides --project backend/UrbanSketch.Financial.Api --output docs/sql/add_financial_model_construction_area_overrides.sql
dotnet ef migrations has-pending-model-changes --project backend/UrbanSketch.Financial.Api
```

Последняя команда подтверждает отсутствие изменений модели относительно snapshot.

## Тестирование и воспроизведение

Существующий консольный HTTP-runner ApiTests переведён с жёсткой привязки к основной PostgreSQL на отдельную SQLite in-memory базу со случайным именем на каждый запуск. Keeper-соединение удерживает её в течение runner, после освобождения среда исчезает. Настройки/User Secrets подключения не читаются; PostgreSQL не открывается. Тестовые проекты/концепции создаются только в этой среде. Финансовый CRUD выполняется внутри откатываемой транзакции; снимки подтверждают сохранность fixture.

`SqliteTestContext` сохраняет decimal как TEXT для точного round-trip без SQLite numeric affinity, UTC сохраняется явным преобразованием. Для двух процентных полей CashFlow оставлена NUMERIC affinity, чтобы существующие CHECK работали в SQLite; расчётов/преобразований денег в double в коде тестов нет. Такая среда проверяет HTTP, EF-проекции, связи и сохранение значений, **но не доказывает** работу миграции на PostgreSQL. PostgreSQL-specific numeric и DDL проверены по миграции/SQL/EF snapshot; фактический прогон миграции на отдельной PostgreSQL остаётся шагом перед её применением.

Команды из корня репозитория:

```powershell
dotnet build backend/UrbanSketch.Financial.Api --no-restore
dotnet run --project tests/UrbanSketch.Financial.ApiTests --no-restore
dotnet run --project tests/UrbanSketch.Financial.SeedTests --no-restore
```

SeedTests без аргументов выполняет только 30 автономных проверок читателя/ограничений импортёра. Аргументы `--database-before` и `--database-after` **не использованы**: исторические DB-тесты импортёра обращаются к основной базе.

HTTP-runner проверяет прежний CRUD и новые сценарии: создание без/с площадями, nullable/0/максимум, POST/GET/list/PUT, очистка каждой площади, старый PUT, независимость моделей, неизменность ТЭП, отсутствие частичной записи при ошибке, строгие токены, приоритет override/источник/unknown. Начальный запуск до реализации подтвердил ожидаемые отказы новых сценариев; после реализации проверки проходят.

Результаты окончательной проверки: **104 HTTP/API-теста, 0 ошибок**, включая **35 новых проверок**; **30 автономных тестов импортёра, 0 ошибок**. Всего 134 успешные проверки. Сборка backend завершена с 0 предупреждений и 0 ошибок. Проверка EF model/snapshot успешна; SQL содержит только ожидаемые операции. Отдельное ревью не выявило ошибок корректности; ограничение SQLite относительно реального PostgreSQL указано выше.

## Безопасное последующее применение

В этой задаче `dotnet ef database update` и SQL не выполнялись, PostgreSQL и демонстрационные записи не изменялись.

Перед применением по отдельному разрешению:

1. Сделать резервную копию целевой БД и проверить восстановление; подтвердить правильное подключение без публикации секретов.
2. Проверить историю миграций: InitialCreate применена, новая миграция ещё отсутствует. Если схема создана вручную или расходится с миграциями — сначала устранить расхождение.
3. Просмотреть SQL и выполнить его на отдельной одноразовой PostgreSQL с копией прежней схемы/данных. Подтвердить сохранность старых строк, NULL новых полей и точный round-trip максимума.
4. Запланировать остановку записей/окно изменения схемы: ALTER TABLE требует блокировки. После разрешения применить **либо** проверенный SQL, **либо** штатное EF-обновление до новой миграции, не оба способа подряд.
5. Только после успешного изменения схемы запускать обновлённый backend против целевой базы: его GET/CRUD уже обращается к новым столбцам. До этого использовать прежний backend или изолированную тестовую среду.
6. Проверить HTTP на специально созданных проверочных моделях, не удаляя пользовательские модели. React ещё не имеет редактора новых полей; старый клиент продолжает сохранять прежние overrides при PUT.

Финансовые формулы, инвалидизация будущих результатов, вычисление неизвестных строительных площадей и пользовательский интерфейс — следующие отдельные этапы.
