# Итоговая приёмка спринта 2 UrbanSketch.pro

Дата технической проверки: **12 ноября 2026 года**, Europe/Moscow.
Ветка: `feature/sprint-2-data-api`; ветка не переключалась.

**Вывод: обязательная функциональность спринта 2 реализована и прошла проверку.
Спринт можно предъявлять заказчику с перечисленными ниже замечаниями. Перед
демонстрацией на обычных портах необходимо вручную запустить актуальный backend:
существующий процесс на 5079 возвращает 404 для `/api/projects`.** Успешная
техническая приёмка проведена на отдельных портах 5190/5174. Решение заказчика
о приёмке этим отчётом не подменяется.

## Frontend и соответствие макетам

Проверены все 17 пунктов frontend из задания на приёмку:

- Проект выбирается, А и Б возвращают разные реальные ТЭП; mock с несколькими
  проектами проверяет смену родителя. Отображаются все 11 карточек и единицы.
- Null показан как «Нет данных», настоящий ноль — как 0 с единицей измерения.
  Строительные площади не подменяются реализуемыми; восемь неизвестных ТЭП
  каждого демонстрационного варианта остаются null.
- Новая форма пуста, содержит ровно 9 обязательных полей. Проверены создание,
  повторное открытие, редактирование, несколько моделей с устойчивыми ID,
  отмена и подтверждение удаления. После ошибки нет ложного успеха.
- Проверены dirty-guards при смене модели/концепции/экрана/новой форме,
  beforeunload, отмена перехода и подтверждённый discard. Сохранение защищено
  от двойного submit; чтения защищены от поздних ответов и гонок.
- Проверены loading, пустые списки, 400 с ошибками полей, 404, 500, сетевые
  ошибки, повреждённый ответ и retry. Реально отключён только собственный
  backend: страница показала ошибку/повтор без вечной загрузки.
- Оба рабочих экрана проверены на **390, 768, 1440 px**: горизонтального
  переполнения нет. Проверены снимки мобильного экрана ТЭП и планшетной формы.
  На малой ширине поля идут одной колонкой, навигация доступна.
- Четыре раздела и общая стилистика макетов первого спринта сохранены:
  тёмная навигация, синий активный шаг, светлые карточки, группы параметров,
  подписи и единицы. Это структурно-визуальная проверка по `mockups/index.html`,
  без утверждения о попиксельном совпадении или отдельной приёмке дизайна
  заказчиком. Макетные цифры результатов/сравнения не связаны с текущей моделью
  и явно обозначены как демонстрационные.

Деньги проходят через точный десятичный текст/BigInt на клиенте и decimal
на backend. Проверен полный предел numeric(20,2):
`999999999999999999.99` сохраняется и повторно открывается с теми же копейками.
Площади на клиенте пока читаются через JavaScript Number; ограничение ниже.

## Backend, PostgreSQL и безопасность проверки

Перед записью подтверждена цель **127.0.0.1:5432 / urbansketch_financial**,
контейнер `infrastructure-postgres-1` healthy, PostgreSQL 17.11. API-тестовый
конфиг читает ASP.NET Core Development/User Secrets и отклоняет другие
host/port/database до подключения. Импортёр также ограничен локальной БД и
Development. Пароли, содержимое `.env` и полная строка подключения не выводились.

Проверены GET `/api/projects`, `/api/projects/{id}`, `/api/projects/{id}/variants`,
`/api/concepts/{id}`, CRUD `/api/financial-models[/{id}]` и
GET `/api/concepts/{id}/financial-models`. Ответы — DTO без циклов навигации.
Невалидный JSON/Guid/тип/масштаб, отсутствующие поля, отрицательные деньги,
нецелый/неположительный срок, лишние и повторные поля отклоняются. Клиент
не может назначить ID/владельца при PUT или записать расчётные результаты.
Проверены HTTP 400/404 и безопасный 500 без внутренних подробностей.

Непосредственно в PostgreSQL через READ ONLY проверены:

| Объект | Результат |
|---|---|
| Таблицы | `projects`, `concept_variants`, `financial_models`, `cash_flows`, `__EFMigrationsHistory` |
| Первичные ключи | Четыре UUID PK; ключ истории по MigrationId |
| Связи | projects → concept_variants → financial_models → cash_flows, три обязательных FK, один ко многим |

## Замечания и действия перед сдачей

Критических ошибок обязательных сценариев спринта 2 не выявлено. Остались
следующие технические и организационные замечания:

1. **Обычный запуск — исправить перед демонстрацией.** На момент итогового
   запроса `localhost:5079/api/projects` возвращает 404; `localhost:5173`
   отвечает 200, но обычная пара портов не принята как рабочая интеграция.
   Владелец должен вручную завершить/перезапустить свой устаревший backend
   с актуальной сборкой и Development/User Secrets либо демонстрировать
   явно документированную проверенную пару 5190/5174. Автоматического
   завершения существующего backend не выполнялось.
2. **Строительные площади — открытое требование ТЗ §5.1.** До реализации
   расчёта затрат в спринте 3 предусмотреть ручной ввод либо коэффициент,
   согласовать владение этими значениями. Сейчас они принадлежат концепции,
   а не отдельной модели. В объёме спринта 2 данные предусмотрены корректно;
   полную готовность входов расчёта заявлять нельзя.
3. **Точность экстремальных ТЭП — известное ограничение.**
   `frontend/src/api/http.ts` использует JSON.parse для обычных DTO,
   `api/client.ts` и `formatTep.ts` работают с Number. Воспроизведение без БД:
   `JSON.parse('{"area":9999999999999999.99}').area` даёт
   `10000000000000000`. Исходный numeric(18,2) допустим в БД; его отображение
   теряет точность. Демонстрационные ТЭП и денежный CRUD этим не затронуты.
   Решение: точное чтение/форматирование decimal-площадей либо согласованный
   допустимый диапазон. Учесть до использования этих DTO в расчётах;
   расчёт на backend должен использовать исходный decimal, а не округлённый UI.
4. **Метаданные/инструкция.** README по-прежнему описывает первый спринт;
   `/api/health` возвращает `sprint: 1` и не проверяет доступность БД.
   Перед передачей материалов актуализировать стартовую инструкцию и
   описание текущего состояния. Стадийные docs/09–16 сохраняются как история,
   их прежние ограничения не означают текущий повторный отказ миграции.
5. **Подготовка поставки Git.** Основная часть реализации и документации
   пока untracked; её наличие в рабочей копии не гарантирует включения
   в будущую передачу. Отдельно подготовить комплект исходников/документов
   и исключить ранее отслеживаемый `frontend/tsconfig.tsbuildinfo` из будущей
   поставки как генерируемый кэш. В этом аудите staging/commit не выполнялись.

Пункты 1, 4 и проверка комплекта из пункта 5 необходимы для корректной
демонстрации и передачи. Пункты 2–3 следует явно принять как ограничения
этапа данных и закрыть при подготовке входов расчёта; они не превращают
расчёты спринтов 3–4 в долг спринта 2. Требования о финансовых расчётах,
потоках, сравнении и CSV не предъявляются досрочно.
